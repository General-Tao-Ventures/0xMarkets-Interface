<objective>
Add an RPC-based polling fallback that detects execution/cancellation events when WebSocket misses them, and add a timeout mechanism so toasts never stay stuck on "Pending..." forever.

Purpose: The existing WebSocket event subscription (`subscribeToV2Events`) works in ideal conditions but misses events when the WS connection drops silently on Base Sepolia. This plan adds a safety net that polls via standard RPC `eth_getLogs` for pending operations, ensuring every deposit, withdrawal, and order gets its execution/cancellation detected.

Output: A new `useExecutionPolling` hook integrated into `SyntheticsEventsProvider` that catches missed events.
</objective>

  <files>src/context/SyntheticsEvents/useExecutionPolling.ts</files>
  <action>
Create a new hook `useExecutionPolling` that polls for execution/cancellation events via RPC `eth_getLogs` as a fallback when WebSocket events are missed.

**Design:**

1. Accept parameters:
   - `chainId: number`
   - `depositStatuses: DepositStatuses`
   - `withdrawalStatuses: WithdrawalStatuses`
   - `orderStatuses: OrderStatuses`
   - `setDepositStatuses`, `setWithdrawalStatuses`, `setOrderStatuses` (state setters)
   - `enabled: boolean` (to disable when WS is healthy)

2. Identify "stuck" operations: operations that have `createdTxnHash` but NO `executedTxnHash` and NO `cancelledTxnHash`, and where `Date.now() - createdAt > POLL_DELAY_MS` (e.g., 10 seconds -- give WS a chance first).

3. For stuck operations, call `provider.getLogs()` on the EventEmitter contract address, filtering for:
   - `EventLog` topic (from EventEmitter ABI) with the event name hash as topic1
   - Use hashes: `DEPOSIT_EXECUTED_HASH`, `DEPOSIT_CANCELLED_HASH`, `WITHDRAWAL_EXECUTED_HASH`, `WITHDRAWAL_CANCELLED_HASH`, `ORDER_EXECUTED_HASH`, `ORDER_CANCELLED_HASH`
   - Block range: from the block of `createdTxnHash` to "latest"

4. Parse returned logs using the same `parseEventLogData` function from `subscribeToEvents.ts` (export it). Extract the `key` from `bytes32Items.items.key` and the `transactionHash`.

5. If a matching execution/cancellation log is found for a stuck operation, update the corresponding status using the same pattern as the WS handlers (e.g., `setDepositStatuses((old) => updateByKey(old, key, { executedTxnHash }))`).

6. For operations stuck beyond `MAX_WAIT_MS` (5 minutes / 300 seconds) with no execution AND no cancellation found via polling, mark them with a synthetic `cancelledTxnHash` of `"timeout"` so the toast transitions to an error state. The `GmStatusNotification` already handles `cancelledTxnHash` as an error.

**Constants:**
```typescript
const POLL_INTERVAL_MS = 5_000;       // Poll every 5 seconds
const POLL_DELAY_MS = 10_000;         // Wait 10s before first poll (give WS a chance)
const MAX_WAIT_MS = 5 * 60 * 1000;   // 5 minutes max before timeout
```

**Implementation pattern:**
```typescript
export function useExecutionPolling({
  chainId, depositStatuses, withdrawalStatuses, orderStatuses,
  setDepositStatuses, setWithdrawalStatuses, setOrderStatuses,
}: ExecutionPollingParams) {
  const provider = getProvider(undefined, chainId);

  useEffect(() => {
    // Collect stuck operations
    const stuckDeposits = Object.values(depositStatuses).filter(isStuckOperation);
    const stuckWithdrawals = Object.values(withdrawalStatuses).filter(isStuckOperation);
    const stuckOrders = Object.values(orderStatuses).filter(isStuckOperation);

    if (stuckDeposits.length === 0 && stuckWithdrawals.length === 0 && stuckOrders.length === 0) return;

    const interval = setInterval(async () => {
      // For each stuck operation, poll eth_getLogs
      // If found, update status
      // If timed out (> MAX_WAIT_MS), mark as timeout error
    }, POLL_INTERVAL_MS);

    return () => clearInterval(interval);
  }, [/* deps */]);
}
```

**IMPORTANT:** The `parseEventLogData` function is currently defined locally inside `subscribeToEvents.ts`. It needs to be exported. However, to avoid modifying that file in this task, re-implement the minimal parsing needed: for execution/cancellation events, we only need to extract `bytes32Items.items.key` from the event data. Use the EventEmitter ABI to parse logs via `eventEmitter.interface.parseLog(log)` -- the same approach `handleCommonLog` uses in `subscribeToEvents.ts`.

**IMPORTANT:** Use `useRef` for the statuses to avoid re-creating intervals on every status change. The interval callback should read from refs, not from stale closure values. Pattern:
```typescript
const depositStatusesRef = useRef(depositStatuses);
depositStatusesRef.current = depositStatuses;
```

Do NOT use lingui `t` or `Trans` in this utility hook -- it's pure logic, no UI strings.
