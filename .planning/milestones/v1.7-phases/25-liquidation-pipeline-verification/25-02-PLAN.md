From keeper-service database (Prisma schema -- status flow):
- LiquidationCandidate: NEW -> PENDING -> EXECUTED (or FAILED)
- LiquidationExecution: SUBMITTED -> MINED (or REVERTED/DROPPED)

From keeper-service/src/core/scanner.ts:
- Auto-discovers accounts via positionFetcher.discoverAccountsWithPositions()
- For each position: getMarket() -> getMarketPrices() -> checkLiquidatability()
- If liquidatable: savePositionSnapshot -> createCandidate(NEW) -> signDecision -> executor.execute()

From keeper-service/src/core/executor.ts:
- execute(): getPositionSnapshot -> fetchAccountPositions -> buildOracleParams -> executeLiquidation -> createExecution(SUBMITTED) -> updateCandidate(PENDING)

From keeper-service/src/core/confirmator.ts:
- Watches EventLog2 for "OrderExecuted" events
- Filters for liquidation orders (orderType === 7)
- Updates execution SUBMITTED->MINED, candidate PENDING->EXECUTED

IMPORTANT: Use WETH/USD market (most reliable oracle data). Avoid JPY/USD (known oracle data gaps).
IMPORTANT: The order-execution-keeper must be running to push fresh prices to PythLazerFeedProvider. Without it, scanner rejects all prices as stale.
IMPORTANT: Shared wallet nonce conflict risk -- do not run other E2E tests while the liquidation pipeline is executing.

**Key design decisions:**
- Use WETH/USD market (reliable oracle, no JPY data gaps)
- Use minimal collateral ($1 USDC = 1_000_000 at 6 decimals) with high size ($50 = 50n * 10n**30n at 30 decimals) for ~50x leverage

4. Submit via ExchangeRouter.multicall (sendWnt + sendTokens + createOrder)
5. Extract operation key from transaction receipt (use `extractOperationKey` from helpers.ts)
6. Wait for order execution by the order-execution-keeper (use `waitForExecution` from helpers.ts)
7. Log the position details: account address, market, collateral amount, size, estimated leverage
