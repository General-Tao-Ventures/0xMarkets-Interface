    **FIX-03: WebSocket CLOSING state handling**

    The "Dropping duplicate message" spam comes from ethers.js WebSocket provider internally when messages arrive during CLOSING state. The fix is to prevent sending to a CLOSING WebSocket and handle reconnection more cleanly.

    1. In `src/lib/rpc/index.ts`, update `closeWsConnection`:
       - Before calling `wsProvider.websocket.close()`, also remove all listeners to prevent duplicate event processing during shutdown.
       - The current code already checks `isProviderInClosedState` which includes CLOSING, so the guard exists. But ensure `removeAllListeners` happens BEFORE the close check, not after, to prevent the duplicate message window.

    2. In `src/context/WebsocketContext/WebsocketContextProvider.tsx`, in the `healthCheckEffect`:
       - Before calling `wsProvider.listenerCount()`, check if the provider is in CLOSING state first:
         ```
         if (isProviderInClosedState(wsProvider)) {
           // Provider is closing/closed, trigger reconnect without logging spam
           const nextProvider = getWsProvider(chainId);
           setWsProvider(nextProvider);
           initializedTime.current = Date.now();
           return;
         }
         ```
       - This prevents the health check from interacting with a CLOSING websocket, which causes the duplicate message spam.
       - Suppress the development-only console.log for health checks that are just confirming state — only log when something actionable happens (reconnection).

    **FIX-04: Metrics batch_report endpoint**

       Per user decision: Claude's discretion on store vs discard — discarding is correct here since testnet metrics have no operational value yet.

    4. In `src/lib/oracleKeeperFetcher/oracleKeeperFetcher.ts`, update `fetchPostBatchReport` to silently catch errors:
       - Add `.catch(() => new Response())` to the fetch call so that if the endpoint still fails for any reason, it returns a silent empty response instead of throwing/logging.
       - This is the belt-and-suspenders approach: keeper has the endpoint AND frontend suppresses failures.
